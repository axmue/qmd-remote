# qmd 2.9.0 upgrade — implementation review (2026-11-21)

Spec (`docs/specs/qmd-remote.md`, D1–D14), plan (`docs/tmp/qmd-2.9.0-upgrade.md`,
D-A…D-E, P1–P4) and ADR-0004 describe one coherent change: pin `@tobilu/qmd`
2.8.3 → 2.9.0, retire the ADR-0003 global-default seam (hole closed upstream),
re-wire the surviving `searchVector` closure wrinkle for 2.9.0's internal
signature, and adopt the metadata surface across MCP and CLI. Commits
`7f1b65b..89a57c8` (P1–P4) implement exactly that. The seam re-wire was
verified line-by-line against `node_modules/@tobilu/qmd` 2.9.0's own
`store.searchVector` body (dist/index.js:323-326) and internal `searchVec`
(store.js:2458 wrapper, :4432 impl); the MCP copy was diffed against
`dist/mcp/server.js` (query/get/multi_get/status/metadata) and is verbatim on
the tool surface; the drift check was mutation-tested and is stronger than
before. Two of the plan's explicit test bullets were not implemented (MCP
`searches` branch; clean-machine test update), and one user-visible count was
re-worded without the spec recording it.

## Verdict

**Pass with findings.** The change is faithful to spec and plan, the seam
facts are correct against the installed 2.9.0 dist, and both green-checkpoint
commands are green. Findings are one stale comment that now asserts a removed
mechanism, one misleading count wording, and two missing test cases named in
the plan — none blocks this change.

## Fidelity

### Spec gaps (spec → plan)

None. Every spec delta the upgrade implies is in the plan: D2 amendment
(global-seam retirement, ADR-0003 superseded), D5 pin move, D8 CLI additions
(`query --filter`, `collections metadata`, status hint), D14 sunset
re-assessment. D-A…D-E map one-to-one onto spec decisions with no dropped
requirement and no spec violation introduced by the plan.

### Plan deviations (plan → implementation)

1. **P1 "CLI clean-machine test updated to assert the hack is gone" — not
   done.** `tests/cli.test.ts:165-173` keeps its pre-change comment block,
   which now *asserts a mechanism that no longer exists* ("createStoreRemote
   now sets qmd's global default to the composite … with the fix"). The test's
   assertions are still valid and still prove the no-download promise
   (2.9.0 routes chunking through the store's llm), but the comment is now
   factually wrong and will mislead the next reader of the regression proof.
2. **P2 "mcp.test.ts (tools/list, query with `searches`, filter, metadata
   call)" — the `searches` case is missing.** No test anywhere drives the MCP
   `query` tool with `searches` (i.e. the `store.search({ queries })` /
   structuredSearch branch, `src/mcp.ts:355-356`). That branch ships to users
   with zero test coverage.

   (P1's "e2e-seam.test.ts updated" required no change — the file is untouched
   and still green, so it is treated as a non-deviation.)

### Undocumented decisions

1. **CLI re-words the upstream metadata count.** Upstream's status line is
   "N keys across M **files with metadata**" (`countDocumentsWithMetadata`,
   dist/cli/qmd.js:412). Ours uses `listMetadata().documents` = active
   documents **in scope** (metadata-store.js:241 `countActiveDocuments`),
   because `countDocumentsWithMetadata` is not exported from the package
   entry (verified). The code comment (`src/cli.ts:252-257`) documents the
   *reason* but the resulting wording ("1 key across 3 files" when only 1 file
   carries metadata) reads as the upstream meaning — see Warnings. The spec's
   D8 bullet ("`status` metadata hint line") does not record the divergence
   from upstream's semantics; add one sentence to D8 or ADR-0004 decision 4.
2. **MCP `metadata` text rendering is our own, not verbatim.**
   `formatMetadataSummaries` (src/mcp.ts) replaces upstream's unexported
   `formatMetadataKeySummaries`. Documented in a code comment (src/mcp.ts,
   tool header + function doc) but ADR-0004 decision 4 says "the MCP copy was
   re-synced verbatim" — true for names/descriptions/schemas (verified) but
   not for this renderer. Add the clause to the ADR (decision 4) so the
   verbatim claim is scoped.

### Test sufficiency

Everything ADR-0004's Verification section claims is covered by failing-without-
the-change tests: `searchVector` filter pass-through + malformed-filter
rejection before search (P1); MCP `metadata` tool, `query` filter, malformed
filter → content-error not crash (P2); CLI `--filter` (valid + invalid +
lex-only path), `collections metadata` table + `--json`, status hint
presence/absence (P3). Consumer gate exercises metadata + filtered query from
outside the package. Gaps: the `searches` branch (Plan deviation 2);
`collections metadata <name>` (positional collection arg),
`--key-limit`/`--key-offset` flag handling, and the
`MetadataBindingBudgetError` path in both MCP and CLI have no tests. The
repo's Done-When conditions map to executable checks (`npm run check`,
`test:consumer`) and both were run.

## Findings

### Critical (must fix)

None.

### Major (should fix before a release)

1. `tests/mcp.test.ts` — the MCP `query` tool's `searches` branch
   (`src/mcp.ts:355-356`, `store.search({ queries })` → structuredSearch) has
   no test, though plan P2 explicitly listed "query with `searches`".
   Fix: one more `client.callTool({ name: "query", arguments: { searches:
   [{ type: "lex", query: "banana smoothie" }] } })` in the existing fixture
   test — it already has everything needed.

### Warnings (should fix)

1. `tests/cli.test.ts:165-173` — clean-machine proof comment still describes
   the retired `setDefaultLlamaCpp` global seam ("createStoreRemote now sets
   qmd's global default to the composite … with the fix"). Plan P1 said this
   test would be "updated to assert the hack is gone"; it wasn't. Rewrite the
   comment: 2.9.0 chunks via `chunkDocumentByTokensWithLlm(store.llm, …)`,
   the global-seam step is gone, the test remains the regression proof.
2. `src/cli.ts:259` (status) and `src/cli.ts:469` (`collections metadata`
   header) — "N keys across M files/documents" uses `listMetadata().documents`
   (all in-scope documents), while upstream's identical phrasing counts files
   **with** metadata. "Metadata: 1 key across 3 files" implies all 3 files
   carry metadata (only 1 does — the tests even assert the 3). Fix: reword to
   disambiguate scope (e.g. "1 key across 3 indexed files") or phrase it as
   "in N indexed files"; the test assertions must move with the wording.

### Suggestions (consider)

1. `src/store-remote.ts:141-151` — the filter is parsed *inside* the
   `withLLMSessionForLlm` callback (session opened first); upstream parses
   `opts.filter` before opening the session (dist/index.js:324-325). Harmless
   (the session is released in `finally`, and the malformed-filter test holds)
   but it breaks the "mirrors qmd's own body" claim by one line — hoist the
   parse above the call.
2. `src/cli.ts:438-452` — `collections metadata <name>` with an unknown
   collection name reports "Metadata: none (add qmd.metadata frontmatter…)"
   (silently: `listMetadata` just scopes to a nonexistent collection).
   Upstream validates the name via the collection list. Consider a usage error
   naming the unknown collection.
3. `src/cli.ts:444` (and `src/cli.ts:258` status) — `MetadataBindingBudgetError`
   is caught in the MCP metadata tool but not in the CLI paths; a
   pathological index would crash with a raw stack. Upstream CLI catches it
   and exits 1 with a message (dist/cli/qmd.js:1773-1778). Cheap to mirror.
4. ADR-0004 decision 4 — scope the "verbatim" claim (tool names/descriptions/
   schemas verbatim; `metadata` text renderer and CLI count wording are ours):
   fold in the two "undocumented decisions" above.

## Improvements for next time

- **Pin test bullets to the plan's phase checklists.** Both missing tests
  (`searches` branch; clean-machine test update) were explicit plan bullets
  that silently dropped. In the plan template, give each phase's "Tests:"
  bullet the same status-marking as the phase itself (P2 "done" while one of
  its named tests doesn't exist); the reviewer's fidelity leg then catches it
  mechanically.
- **When porting a count line from another tool, name the denominator.** The
  status hint copied upstream's *wording* but not its *count source*
  (`countDocumentsWithMetadata` vs `countActiveDocuments`). Spec D8's bullet
  should have said "status metadata hint line (documents-in-scope count;
  upstream's with-metadata count is not public)" — one sentence would have
  recorded the divergence and flagged the wording risk at spec time.
- **The drift check's string-literal stripper should be regression-tested.**
  The `}}`-truncation fix was verified by hand (mutation run). A tiny
  `scripts/check-mcp-drift.test.mjs` (or a test-file case) asserting
  "rename a key after a describe with nested braces → drift reported" would
  make the check's own strength durable — it is the gate for the verbatim
  copy, so it deserves a test that fails without it, like everything else in
  this repo.
