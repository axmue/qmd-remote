# Code review — qmd-remote (specs in `docs/tmp/` vs. `src/`)

**Reviewer:** agent · **Date:** 2026-11-10 · **Commit:** `20eae2c`
**Scope:** `src/` (1 522 LoC), `tests/` (1 013 LoC), `scripts/consumer-test.mjs`,
`package.json`, `README.md`, specs `docs/tmp/qmd-remote-*.md`.
**Verified by running:** `npm run typecheck` (clean), `npm test` (35/35 green,
5.4 s), plus three manual probes against the built `dist/` (doctor with a dead
provider, `status --json` on a real temp index, qmd's own path resolution in
`node_modules/@tobilu/qmd/dist`).

---

## Verdict in one paragraph

The package does what the spec says it does, and the hard part — a **patch-free
injection seam** into stock qmd — is genuinely proven, not asserted: the e2e
seam test drives `update()` + `embed()` + `search()` through a mock provider on
a real unpatched store, and the consumer test re-proves it from a packed
tarball. Code style is consistent and unusually well-commented (every
non-obvious decision carries a *why*). The main gaps are (1) one **functional
bug in the headline `doctor` command** (a dead expand provider reports OK /
exit 0), (2) **no secret handling beyond plaintext JSON**, (3) **no retry /
429 handling** for exactly the providers the package targets, and (4) **stock
qmd's project-local `.qmd/index.yml` layout is silently ignored**, which dents
the "same files as qmd" promise. None are architectural; all are
half-a-day fixes. Publish-blocking: #1 and #2.

## 1. Does it make sense? Does it do what's intended?

**Yes, on both counts.** The spec's central bet (D2: `store.internal.llm = backend`
instead of a dist patch) is verified by code reading *and* by test, and the two
closure-capture wrinkles that the bet implies (`searchVector`'s stale model
name, `close()` disposing the pre-swap instance) are both handled in
`src/store-remote.ts:84-104` with comments pointing at the reason. That is the
difference between a wrapper that works and a wrapper that works for three
weeks.

Traceability spec → code is excellent:

Two places where the **plans record conclusions the code contradicts**, which
matters because the plans are the only design docs:

- P3/P4 both claim `getStatus().collections` "comes back EMPTY after a YAML
  sync (verified empirically)" and justify workarounds in the CLI and in the

- P1/P2 call `defaultQmdDbPath` / `defaultQmdConfigPath` a faithful mirror of
  stock qmd; it is 90 % faithful (see §4.4).

## 2. Bugs (functional)

### 2.1 `doctor` cannot detect a broken expand provider — **publish blocker**

`doctor` is the package's headline usability feature ("pay 5 s now, not 30 min
later"), and for the expand job it is a no-op. `expandViaComplete`
(`adapters/shared.ts:103-114`) deliberately swallows provider errors and
degrades to the original query (mirroring qmd's local fallback), so
`backend.expandQuery()` **never throws** — and `cmdDoctor` probes the expand
job through exactly that method (`cli.ts:304`).

Reproduced against the built CLI with expand pointed at a dead port:

```
qmd-remote: remote query expansion failed: … fetch failed   ← stderr, easy to miss
config  /tmp/qr-probe/c.json
expand  openai-compat  OK 2 variants, 12 ms                  ← reported GREEN
EXIT=0                                                       ← exit 0
```

The log line on stderr is the only signal, and `doctor`'s own contract (exit 1
on any failed probe) is violated. Fix: probe expand via `backend.generate()`
(which does throw), or have the adapter expose a `probe()`; and consider
counting a degraded expansion as a WARN line. Same blind spot applies at
runtime: every search silently loses query expansion if the expand provider is
down — arguably acceptable (it is qmd's own semantics) but it contradicts D7's
"a job configured remote NEVER silently falls back", and nothing in
README/spec tells the user that expand is the one exception. Document it.

### 2.2 `process.exit(0)` in the MCP shutdown path

`cli.ts:347` exits hard after `store.close()`. Any buffered stdout write (the
SDK may still be flushing a response frame) is dropped. Prefer
`process.exitCode = 0` + letting the loop drain, as `main()` already does
everywhere else.

### 2.3 `cmdMcp` relies on `stdin` `"close"`

`process.stdin.once("close", …)` fires only because the SDK's stdio transport
puts stdin in flowing mode. If a future SDK version lazily attaches, the server
never shuts down and leaks a process (plus a sqlite handle) per agent restart.
Listening for `"end"` as well is one line and removes the coupling.

### 2.4 `embedBatch` all-or-nothing vs. qmd's `(result|null)[]` contract

Both adapters throw when the provider returns fewer embeddings than inputs
(`openai-compat.ts:88`, `ollama.ts:95`). qmd calls `embedBatch` in batches of
32 (`dist/store.js:1529`) and *is* able to handle per-item `null`
(`recordFailure(chunk, "batch embedding returned no vector")`). Throwing turns
one bad input into 32 failed chunks. qmd's `retryFailedChunks` + 80 %-error
abort limits the blast radius, so this is a quality issue, not a data-loss one
— but returning `null` for the missing index is strictly better and matches the
surface being mirrored.

## 3. Security

No injection sinks, no `child_process` with user input, no `eval`, no dynamic
import of user-controlled paths, correct timeout on every fetch
(`AbortSignal.timeout`), and the error messages deliberately carry URL + status
but not the key. The gaps are about **secrets at rest and data flow**:

1. **API keys live in plaintext JSON with no mode check and no indirection.**
   `~/.config/qmd-remote/config.json` is created by the user (so often `0644`),
   and the schema has no `apiKeyEnv` / `${ENV}` / `file:` form — D9's "no env
   overrides in v1" is reasonable for *routing*, unreasonable for *credentials*.
   Minimum: `loadRemoteConfig` warns on stderr when the file is group/world
   readable; better: accept `"apiKey": "env:OPENROUTER_KEY"`. This also matters
   for the MCP story, where P5b's documented agent config duplicates the config
   path into an agent JSON file that is itself frequently committed.
2. **No redaction of provider response bodies.** `postJson` echoes up to 300
   bytes of the error body into the exception, which surfaces in CLI stderr and
   in MCP tool errors. Some gateways echo the request (including
   `authorization`) in 4xx payloads. A `Bearer\s+\S+` → `Bearer ***` scrub in
   the one place that formats errors is cheap insurance.
3. **`http://` + `apiKey` is accepted silently.** `isValidHttpUrl` allows
   plain http (correct — Ollama needs it) but nothing warns when a key is sent
   over cleartext to a non-loopback host. One `console.error` warning in
   `normalizeJob`.
4. **Privacy is the feature and it is undocumented.** The whole point of the
   package is that document bodies, titles and queries leave the machine for a
   third party (OpenRouter/Jina) — `rerank` ships up to 8 000 chars of document
   text per candidate. The README's unofficial-disclaimer paragraph should gain
   one sentence about what leaves the box; today nothing says it.
5. Minor: a user-supplied `headers.authorization` is silently overridden when
   `apiKey` is set (`shared.ts:33-34`). Last-write-wins is fine; say so in the
   README or error on the conflict.
6. Inherited, not introduced: the MCP server exposes arbitrary file reads
   within indexed collections (`get`, `multi_get` glob) — identical to stock
   qmd, resolved by qmd's own path logic. Worth a line in the README's MCP
   section because the server now runs in places stock qmd wouldn't.

## 4. Code quality

### 4.1 What's good

- **Comment discipline is the standout.** Every module header states what it
  mirrors upstream, at which pinned version, and why the mirror exists
  (`factory.ts:1-34` on tokenization, `mcp.ts:1-18` on the verbatim copy,
  `store-remote.ts:1-18` on the two wrinkles). Six months from now this is
  still maintainable by someone else.
- **Validation is loud and path-naming.** `normalizeJobs` rejects unknown keys
  per level with `jobs.embed.baseUrl`-style paths — the single best usability
  decision in the codebase.
- **Tests are behaviour-level and offline.** Loopback mock with per-URL hit
  recording, spawn tests against the *built* dist (`pretest: npm run build`),
  the e2e seam proof, and a consumer test that installs a real tarball. 35
  tests in 5.4 s with zero network. The assertion "update() must not embed"
  (hits === 0) is exactly the kind of negative assertion most suites lack.
- **No runtime dependency creep**: plain `fetch`, hand-rolled argv parsing,
  only the MCP SDK + zod pinned to qmd's own versions.

### 4.2 Style nits

- `cli.ts:435` has `/* eslint-disable @typescript-eslint/no-floating-promises */`
  but there is no ESLint (or Prettier) in the repo — dead directive, and no
  `lint`/`format` script. Either add the tooling or drop the comment.
- Unused parameters kept for signature parity: `options` in both adapters'
  `rerank` (the `options.model` override is accepted and ignored — a caller
  passing a per-request model gets the configured one silently), `_i` in
  `openai-compat.ts:110`, `context` in `expandQuery` (qmd passes it; we drop
  it). Either honour them or document the drop in the type.
- `byIndex.set(d.index ?? i, d.embedding!)` — the `!` is a lie that the next
  line catches anyway; use the nullable type.
- `openStore()` discards `loadRemoteConfig().source`, so every command except
  `doctor` is silent about which config it used; a `--verbose`/stderr line would
  save support questions.
- `detokenizeAllRemote` chunks at 8 192 to dodge the spread-arg limit — correct,
  but `Buffer.from(Uint16Array.from(tokens).buffer).toString("utf16le")` is one
  line and faster. Taste.
- Line lengths run to ~190 chars in `config.ts`/`cli.ts` single-line throws;
  consistent with itself, but a formatter would be kinder to diffs.

### 4.3 Structural notes

- `cli.ts` mixes argv parsing, output formatting and orchestration in one
  443-line file. Fine at this size; the first thing to split if `--json`
  spreads or commands get options matrices (the `Parsed` struct already carries
  flags irrelevant to most commands, and nothing rejects
  `qmd-remote status --force --lex-only`, which is accepted and ignored —
  per-command flag validation is missing and would be caught by a table-driven
  parser).
- `importLlamaCppCtor()` (`factory.ts:85-101`) walks up for
  `node_modules/@tobilu/qmd/dist/llm.js`. Works for npm/hoisted trees; **breaks
  on pnpm's symlinked store, Yarn PnP, and any bundled deploy** — all of which
  are plausible for an npm-published package. Only local jobs hit this path, so
  the all-remote flagship case is unaffected, but the thrown message ("is
  node_modules present?") will be wrong and confusing for pnpm users. Try
  `import.meta.resolve("@tobilu/qmd")` + `../dist/llm.js` first and keep the
  walk as fallback (the consumer test already learned that
  `import.meta.resolve` is the right tool for this tree).
- `mcp.ts` is ~300 lines of verbatim upstream copy. That is the spec's
  deliberate choice (D3) and the header says so, but there is **no drift
  detector**: a qmd bump changes behaviour upstream and nothing fails. The D11
  CI job should diff our copied blocks against
  `node_modules/@tobilu/qmd/dist/mcp/server.js` (even a checksum of the
  extracted description strings) so re-sync is forced, not remembered.

### 4.4 Stock-location mirroring is incomplete (D6 risk)

`defaultQmdConfigPath` hardcodes `index.yml` and the global location. Stock qmd
additionally supports:

- **project-local configs**: `findLocalConfigPath()` walks up for
  `.qmd/index.yaml|.yml` and pairs it with `.qmd/index.sqlite`
  (`dist/collections.js:74-96`). A qmd user inside such a project runs
  `qmd-remote query` and silently gets the *global* index — the single most
  likely "why does it find nothing?" support ticket.
- **named indexes**: `${currentIndexName}.yml`, not just `index.yml`.
- `qmdHomedir()` honours `HOME`/`USERPROFILE` before `os.homedir()`; our mirror
  uses `os.homedir()` only (irrelevant on POSIX, divergent on odd Windows/CI).

Either call qmd's own resolvers where they are reachable, or implement the
local-config walk — it is ~15 lines and directly serves the "instant migration
for existing qmd users" promise.

## 5. Is it practical and usable?

**For the stated target (GPU-less box, remote embed/rerank, agent via MCP):
yes**, and the P5b walkthrough is a genuinely good onboarding doc. Friction
points, roughly in order of how often a real user will hit them:

1. **No retry/backoff and no 429 handling.** The named targets (OpenRouter,
   Jina) rate-limit aggressively; a 30-minute re-embed will meet a 429. Today
   that is a hard throw for the whole 32-chunk batch; qmd's own retry softens
   it, but an exponential backoff honouring `Retry-After` inside `postJson` (for
   429/5xx only, 2-3 attempts) converts the most common real-world failure from
   "errors: 400" to "slower". This is the top practical gap.
2. **No concurrency/size control.** One request per 32 chunks, no parallelism
   (slow on high-latency APIs), no splitting if the provider caps input count or
   payload size. `maxBatchSize` per job would cover providers with an 8-input
   cap.
3. **No cost/volume signal.** Nothing tells the user "this will embed 12 400
   chunks ≈ 9 M tokens" before `embed` runs against a paid endpoint. A dry-run
   line in `status`/`embed` (chunk + byte counts are already in the DB) would be
   a big trust win for a tool whose purpose is sending data to a metered API.
4. **Two different "config" concepts, one flag name.** `--config` means qmd's
   `index.yml`; the *jobs* config is env-var-only (`$QMD_REMOTE_CONFIG`). A
   `--jobs <path>` flag (and a `doctor`-printed resolution) removes a predictable
   confusion. There is also no `qmd-remote config init` to scaffold the JSON —
   the README/P5b examples are the only source of the shape.
5. **`query` can't search text starting with `-`** (no `--` separator), and
   `query -n 0` is a usage error but `query --force` is accepted and ignored.
6. **No `--version`.** `--help` exists; `qmd-remote --version` is the first
   thing a user types when filing a bug.
7. Progress output truncates at a hardcoded 80 columns and writes `\r` even when
   stderr is not a TTY (log files get carriage returns). `process.stderr.isTTY`
   check.
8. `embed` returning exit 1 on partial errors while printing "provider errors
   are shown above" — qmd logs them, but the CLI never aggregates them. An
   error-reason histogram would make the common failure self-service.

## 6. Process / docs hygiene (vs. AGENTS.md)

- The spec and all six phase plans live in `docs/tmp/` only. AGENTS.md's
  promotion rule ("on completion: spec → `docs/specs/`") hasn't fired, and
  `docs/arch/`, `docs/specs/`, `docs/dev/`, `docs/adr/` — all referenced by
  AGENTS.md — don't exist. The spec is stable and shipped; promote it.
- `README.md` is still the 12-line stub marked "under construction" and points
  users at `docs/tmp/…`, which is **not in the `files` array** — so the
  published tarball's README would reference a document the consumer cannot
  read. P6 task 2 covers this; it is a publish blocker.
- `private: true` is still set (intentional, P6 gate).
- `AGENTS.md`'s "Done When" section is literally `to be specified` — for a
  project this far along, the done-criteria are knowable (typecheck + 35 tests +
  consumer test 6/6).
- No CI yet (P6/D11), so the pin-bump safety net the whole design leans on is
  still a plan. Given that `mcp.ts` is a verbatim copy and
  `factory.ts`/`store-remote.ts` reach into `dist` internals, CI is not optional
  polish — it is the maintenance model.
